## 3. Release-level constraints

- **v2.0.0 is the compatibility baseline.** v3.0.0 is additive around the released compiler,
  runtime, artifact formats, host ABI, and language profile unless a locked target explicitly
  says otherwise.
- **No new core language or compiler features.** Compiler changes are limited to bug fixes and
  the instrumentation or public views required by a locked target: the rename/reference view
  (WL-18), the manifest optionality audit (WL-17), and any ESI binding validation (WL-7). Each
  change is specified and reviewed as part of that target. WL-1.2 (delivered) added no compiler
  change and no debug-protocol revision.
- **Network-facing work is security work.** WL-1.2 (delivered) and WL-15 define authentication,
  transport security, loopback defaults, explicit network opt-in, secret handling, rate limits,
  and a threat model. They share the threat-model structure and secret-handling stance; WL-1.2
  delegated encryption and peer authentication to SSH, while WL-15 owns its broker TLS and
  credential design. Neither is a safety function.
- **ESI is untrusted input.** WL-7 parsing must be bounded, robust, and fuzz-tested. Vendor ESI
  files may have redistribution restrictions; only synthetic or permission-cleared files are
  committed.
- **WL-14 adds macOS as a supported native host.** macOS ARM64/x86-64 join the support matrix at
  Windows parity for the Windows-available surface, excluding EtherCAT and PREEMPT_RT-style hard
  real time. Neither platform gains a hard-real-time or safety claim. Production scheduler
  behavior is unchanged unless measured evidence and owner review approve an opt-in runtime mode.
- **Evidence over assertion.** Verification claims use the V0–V4 ladder in the
  [Verification Program Plan](specification/Verification/VerificationProgramPlan.md).
  Performance and timing claims record host, OS, build form, metric, and sample.
- **`stc` remains not a safety PLC.** Debug, remote access, I/O, and any scheduling work can
  hold outputs or move machinery; safety must come from a separate system and machine design.
  See [NON-SAFETY.md](NON-SAFETY.md).
- **Existing CI gates remain active.** The 85% line-coverage gate, docs/specification link
  checks, Markdown lint, rule traceability, Lean proofs, fuzz smoke, and package smoke must stay
  green throughout.
- **This plan is retired when the targets are complete.** Durable contracts and evidence move
  to the specifications and verification reports; the working plan and its change log are then
  deleted.

### WL-7 — ESI-based EtherCAT device configuration

Status: Locked 2026-11-04; not started. Size M/L.

**Goal.** Let the runtime configure EtherCAT devices from vendor ESI XML instead of
hand-maintained channel and PDO metadata, building on the delivered WL-5.2 EtherCAT backend.

**Locked scope.**

- Ingest ESI XML from project or runtime configuration, including package-relative paths and a
  vendor file library.
- Parse and validate identity (vendor ID, product code, revision), PDO mappings, sync managers,
  distributed clocks, and mailbox/SDO data. Handle multiple files and revisions with
  deterministic selection and clear diagnostics.
- Map validated slave descriptions to the `stc` device/channel model and to IgH configuration;
  verify at startup that the discovered slave matches the expected vendor/product/revision and
  PDO layout.
- Decide the compiler/runtime split: the compiler may validate binding widths against ESI at
  build time while keeping the language and metadata protocol-agnostic; the runtime owns IgH
  configuration and live verification.
- Define and document the supported ESI subset; reject unsupported or ambiguous input explicitly
  rather than silently ignoring fields.
- Test with synthetic and vendor-format ESI files, malformed/ambiguous/mismatched inputs, a
  simulator, and hardware-in-the-loop on the RT host. Ship only a small curated ESI set for
  tests; users supply vendor files.

**Non-goals.**

- Full ESI/object-dictionary coverage or distributed-clock behavior beyond the documented
  subset.
- Changing the EtherCAT backend semantics, the language, or the protocol-agnostic metadata
  model.
- Motion control or servo-drive commissioning (WL-6 remains deferred).
- Redistributing vendor ESI files without permission.

**Work breakdown.**

1. Define the supported ESI subset, XML validation, identity/revision selection, and
   diagnostics; decide how files are located and version-pinned.
2. Implement the mapping from validated descriptions to the device/channel model and IgH
   configuration.
3. Add startup verification of the discovered slave's identity and PDO layout, and define the
   mismatch/failure policy.
4. Add the optional compiler-side binding-width validation without changing the language.
5. Add synthetic/vendor-format fixtures, malformed/ambiguous tests, fuzz coverage, simulator
   tests, and HIL on the EtherCAT host.
6. Document the subset, failure policy, file handling, and runbook changes.

**Exit criteria.**

- An ESI-described slave configuration produces validated channels/PDOs and IgH configuration.
- Startup verifies the discovered vendor/product/revision and PDO layout, and a mismatch fails
  with a clear diagnostic rather than silently using the wrong layout.
- Malformed, ambiguous, and unsupported ESI inputs fail deterministically with actionable
  messages; the supported subset is documented.
- No vendor file is committed without permission; tests use synthetic or permission-cleared
  files.
- HIL evidence is recorded on the EtherCAT host; no hard-real-time or safety claim is added.
- The language and compiler remain protocol-agnostic; any validation change is documented.

**Evidence.** ESI fixture corpus, parser/fuzz tests, mapping and startup tests, HIL results,
updated [I/O Routing and Backends](specification/Architecture/IO-Routing-and-Backends.md),
[I/O and Devices](specification/Architecture/IO-and-Devices.md),
[CLI and Manifest](specification/Architecture/CLI-and-Manifest.md), and
[Decisions](specification/Decisions.md).

**Dependencies and risks.**

- WL-5.2 is delivered: IgH 1.6.13, the DIEWU slave, and the static configuration path exist.
- ESI is vendor-extended XML; full coverage is unrealistic. The supported subset and rejection
  policy are the main design decisions.
- IgH has its own configuration model; the integration point (generated configuration, library
  API, or both) must be chosen.
- HIL is limited to the available DIEWU hardware; no servo hardware is available.
- ESI parsing is untrusted-input handling and needs bounded, fuzzed code.

**Open planning questions.**

- What is the minimum first subset: identity and PDO mapping only, or also distributed clocks,
  mailbox, and SDO startup parameters?
- Compile-time validation, runtime-only configuration, or both?
- How are ESI files selected, version-pinned, and resolved for deployment?
- Does IgH consume ESI directly or through generated configuration, and which IgH versions are
  supported?
- How is a device mismatch handled: refuse to start, fall back to defaults, or require a cold
  download?
- Where do ESI files live in a package or manifest, and how are they validated at build time?

### WL-14 — macOS native support and Windows/macOS soft-real-time scheduling for tests

Status: Complete 2026-11-09; manually checked and approved; merged into `v3.0.0-planning` (PR #27, merge `e99f33a`). Size M/L.

**Goal.** Make macOS ARM64/x86-64 supported native hosts at Windows parity for the
Windows-available surface: compile, run, debug, VS Code integration, packaging, online change,
state/I/O, remote debug, and the full test suite. EtherCAT and PREEMPT_RT-style hard real time are
explicitly excluded. Add the opt-in soft-real-time scheduling mode on macOS and Windows and record
informational measurements, without claiming hard real time.

**Locked scope.**

- Run `cargo test --workspace --locked` on macOS ARM64 and x86-64 GitHub-hosted runners; fix
  portability failures rather than filtering tests.
- Produce `stc-<version>-<triple>` packages for `aarch64-apple-darwin` and `x86_64-apple-darwin`
  with `debug_contract: dwarf`, Mach-O debug stripping, ad-hoc re-signing, and portable checksum
  verification.
- Support macOS in the VS Code extension: the VSIX is platform-independent, and the real Electron
  smoke runs on both macOS runners.
- Add an opt-in test/benchmark scheduling mode:
  - Windows: raise the cycle/test thread to `THREAD_PRIORITY_TIME_CRITICAL`, and optionally use
    MMCSS (`AvSetMmThreadCharacteristics` with an audio task, then revert) with explicit scope
    and cleanup; avoid requiring administrator privileges.
  - macOS: apply a Mach `THREAD_TIME_CONSTRAINT_POLICY` or appropriate QoS/priority to the
    cycle/test thread; document entitlement or privilege requirements and ARM64/x86-64
    differences.
- Measure cycle timing, wake lateness, and request/scan jitter with the existing WL-4 harness on
  Windows and macOS; compare baseline against scheduling mode; record host, OS, build form,
  metric, and sample. No timing threshold or CI timing gate.
- Update the CI matrix, runbooks, support matrix, decisions, and known limitations; state the
  EtherCAT and PREEMPT_RT exclusions and that neither platform becomes a hard-real-time or safety
  platform.
- Keep production scheduler behavior unchanged unless measured evidence and owner review
  approve an opt-in runtime mode.

**Non-goals.**

- EtherCAT hardware support on macOS.
- PREEMPT_RT-style hard real time on macOS or Windows.
- A hard-real-time or safety claim on any platform.
- WL-12's sub-millisecond wake-jitter investigation or the deferred tuned boot profile; WL-12
  is not in v3 and is not a prerequisite.
- Changing the default runtime scheduler without the evidence and review gate above.

**Work breakdown.**

1. Check GitHub-hosted macOS runner availability, architectures, cost, and scheduling
   privileges; choose the matrix subset (`macos-15` ARM64 and `macos-15-intel` x86-64).
2. Add the macOS jobs and run the full workspace suite; fix portability failures in short Unix
   socket paths, the fake remote GNU userland, and the non-Linux EtherCAT mock.
3. Make `cargo xtask package` Mach-O-aware and add both macOS runners to the package matrix.
4. Add both macOS runners to the VS Code extension smoke with the platform-independent VSIX.
5. Implement the scoped opt-in scheduling mode for Windows and macOS, with cleanup and
   privilege documentation; run the measurement campaign with the WL-4 harness.
6. Update the CI matrix, runbooks, performance notes, support matrix, decisions, and known
   limitations.

**Exit criteria.**

- Both macOS jobs run `cargo test --workspace --locked` and pass.
- Both macOS package jobs build, verify, and exercise the package; `debug_contract` is `dwarf`
  and no `__debug_*` sections remain.
- Both macOS extension-smoke jobs pass activation, LSP, task, and DAP.
- The opt-in scheduling mode works on the platforms where the runners permit it, or the
  blocking privilege/entitlement limitation is documented with evidence.
- Measurements are recorded with host, OS, build form, metric, and sample; baseline and
  scheduling mode are compared, with no threshold or gate.
- Production scheduler behavior is unchanged unless the evidence-and-review gate is explicitly
  met.
- Documentation lists macOS as a supported host and the EtherCAT/PREEMPT_RT exclusions; no
  hard-real-time or safety claim is added.

**Evidence.** Final five-host CI run
[42546445894](https://github.com/r2k-in-the-vortex/stc/actions/runs/42546445894), green on all
jobs including both macOS workspace, package, and extension-smoke jobs; macOS full-workspace runs
[42537537193](https://github.com/r2k-in-the-vortex/stc/actions/runs/42537537193) and
[42541200112](https://github.com/r2k-in-the-vortex/stc/actions/runs/42541200112); macOS package
run [42539220760](https://github.com/r2k-in-the-vortex/stc/actions/runs/42539220760); scheduling
campaign [42521471115](https://github.com/r2k-in-the-vortex/stc/actions/runs/42521471115);
decisions D-249 and D-250; updated [RT-Host.md](specification/Verification/RT-Host.md),
[RT-Runbook.md](specification/Verification/RT-Runbook.md),
[Performance.md](specification/Verification/Performance.md),
[USER-GUIDE.md](USER-GUIDE.md), and [KNOWN-LIMITATIONS.md](KNOWN-LIMITATIONS.md).

**Dependencies and risks.**

- The WL-4 harness and RT runbooks exist; WL-12 is not required.
- The full workspace exposed macOS portability issues: the 104-byte Unix-socket path limit, BSD
  `stat`/`sha256sum` in the fake remote host, and the non-Linux EtherCAT mock. They are fixed in
  the test harness, not by filtering tests.
- Mach-O stripping needs `llvm-strip --strip-debug` and ad-hoc re-signing; the macOS package jobs

- The macOS runners accepted `THREAD_TIME_CONSTRAINT_POLICY`; the QoS fallback remains covered by
  host tests.
- MMCSS behavior for a PLC cycle thread is measured, not assumed; thread priority alone is not a

- Timing tests can be flaky; the project treats flakiness as a bug, not a reason to widen
  deadlines. The measurement campaign defines no threshold.

**Resolved planning questions.**

- Which macOS runner images and architectures? `macos-15` (ARM64) and `macos-15-intel` (x86-64);

  all ten macOS `--rt` runs reported `sched:"time_constraint"`, and the QoS fallback is covered by
  the host tests.
- Is MMCSS appropriate for a cycle thread? It is applied when available; the header records
  `mmcss` or `time_critical`, and the mode remains advisory.
- Which tests run on macOS? The full workspace (`cargo test --workspace --locked`), plus the
  package exercise and the VS Code extension smoke.
- What metric and threshold justify an opt-in scheduling mode? No threshold; `--rt` is opt-in and
  the metrics are informational (D-193, D-249).
- Should the scheduling mode reuse WL-12's wake-lateness metrics? WL-12 is not required; the
  existing WL-4 harness supplies the metrics.

### WL-15 — MQTT client for process-image I/O

Status: Locked 2026-11-04; not started. Size M/L.

**Goal.** Add an MQTT client I/O backend that connects to an external MQTT broker and maps
topic/payload messages to the `stc` process image. The broker is external; this target does not
implement a broker, an MQTT server, or a cloud connector.

**Locked scope.**

- Client role only: connect to one or more configured MQTT brokers; no broker, MQTT server,
  MQTT-SN, or cloud-specific connector.
- Map channels to topics and payloads in the machine profile: subscription topics for inputs,
  publish topics for outputs, payload encoding, retain and last-will, QoS, keepalive, reconnect
  and backoff, and stale/cache behavior.
- Integrate as an `mqtt`/`mqtt-status` kind through `DeviceBackend`; connection lifecycle,
  per-backend fault/status, and optional PLC-visible status fields.
- Support broker authentication and TLS where the broker requires it; document the trust
  boundary and credential handling.
- Provide a deterministic local broker or simulator for tests; do not make the base package
  depend on a broker.
- Record cross-host tests, reconnect and malformed-payload tests, and cycle-overhead
  measurements. No hard-real-time or safety claim.

**Non-goals.**

- Implementing a broker, MQTT server, MQTT-SN, or a cloud-specific connector.
- Hard real-time behavior or interpolated motion over MQTT.
- Shipping a broker or requiring one in the base package.
- Changing the process-image or device-binding model beyond the new backend kind.

**Work breakdown.**

1. Decide the MQTT version (3.1.1 first, 5.0, or both), the client-library or project-owned
   implementation choice, and the payload encodings.
2. Define the machine-profile mapping schema, topic/payload rules, and the `mqtt`/`mqtt-status`
   device kind.
3. Implement the backend through the multi-backend coordinator, with cycle-boundary sampling and
   bounded, non-blocking behavior.
4. Implement connection lifecycle, authentication/TLS, reconnect/backoff, stale/cache policy,
   and status.
5. Add the broker simulator or local test broker, reconnect/malformed tests, cross-host tests,
   and overhead measurements.
6. Update the I/O, CLI/manifest, and known-limitations documentation.

**Exit criteria.**

- The MQTT client backend runs alongside the delivered Modbus TCP and EtherCAT backends on the
  supported hosts.
- The topic/payload mapping is explicit and source-controlled; MQTT payloads have no standard
  PLC register layout.
- A slow or unavailable broker cannot stall the scan; the stale/cache and reconnect policies
  are documented and tested.
- Credentials and TLS material are configured outside source control and follow the shared
  remote-access security design.
- Cross-host, reconnect, malformed-payload, and overhead evidence is recorded.
- The base package has no broker dependency and no hard-real-time or safety claim is added.

**Evidence.** Broker-simulator and mapping tests, reconnect/malformed tests, cross-host
results, overhead measurements, updated
[I/O Routing and Backends](specification/Architecture/IO-Routing-and-Backends.md),
[I/O and Devices](specification/Architecture/IO-and-Devices.md),
[CLI and Manifest](specification/Architecture/CLI-and-Manifest.md), and
[Decisions](specification/Decisions.md).

**Dependencies and risks.**

- The delivered multi-backend coordinator, process-image model, and device-binding contracts are
  the integration points.
- WL-7 (EtherCAT) and WL-1.2 (remote security) are selected alongside this target; WL-15 shares
  the shared threat-model and secret-handling stance, not WL-1.2's SSH transport.
- MQTT is asynchronous and non-real-time; slow brokers and partial failures are the main
  operational risks.
- The test strategy needs a deterministic broker or simulator without making the base package
  depend on one.
- Client-library license, ABI, and maintenance cost are planning decisions.

**Open planning questions.**

- MQTT 3.1.1 first, MQTT 5.0, or both?
- Use an external MQTT client library (and which license/ABI) or a project-owned minimal client?
- What payload encodings are required: raw bytes, BOOL/int/float/string, or JSON?
- Which QoS levels, retained messages, last-will, clean-session, and keepalive defaults?
- How are credentials and TLS material configured and kept out of source control?
- What is the stale/cache policy when the broker disconnects, and how are failures visible to
  the PLC?
- One broker per device, multiple brokers per run, or one broker shared by several devices?
- How does the test suite provide a broker without making the base package depend on one?

### WL-16 — Debug session lifecycle: start-paused binding and exit status

Status: Complete 2026-11-05; manually checked and approved. Size S/M.

**Goal.** Close the two WL-1.1 debug-session follow-ups deferred from v2.0.0: bind breakpoints
before the first cycle (F-9) and report session termination and exit in the Debug Console
(F-15). Optionally surface the `[debug].session-timeout` budget as well.

**Locked scope.**

- Add a start-paused mode or an equivalent ready/bind handshake so breakpoints bind before the
  first cycle. Define launch and attach behavior, the time budget, and the failure path.
- Report terminate and exit in the Debug Console and distinguish a user stop from a host exit,
  trap, or connection loss.
- Optionally surface the `[debug].session-timeout` budget or a warning when the opt-in timeout
  is enabled.
- Keep `stc-debug/1` valid; a start-paused addition is a documented protocol revision.

**Non-goals.**

- Remote debugging (WL-1.2).
- Changing force, breakpoint, or release-monitoring semantics beyond the session-start/exit
  behavior above.
- A safety function; a paused session holds outputs.

**Work breakdown.**

1. Decide whether start-paused is a new protocol message, a launch flag, or an adapter-side
   wait for a ready event.
2. Implement the runtime/start-gate and adapter changes for launch and attach.
3. Implement terminate/exit reporting and the optional timeout budget/warning.
4. Add cycle-0 breakpoint integration tests, terminate/exit and timeout tests, and an extension
   smoke update.
5. Update [Debug and Monitoring](specification/Architecture/Debug-and-Monitoring.md) and
   [IDE Integration](specification/Architecture/IDE-Integration.md).

**Exit criteria.**

- A launch breakpoint at cycle 0 stops before the first cycle, so the first stop observes
  cycle-0 values deterministically.
- Terminate and exit are reported in the Debug Console; a user stop is distinguishable from a
  host exit, trap, or connection loss.
- The optional timeout budget or warning is documented if implemented.
- `stc-debug/1` remains valid; the revision is documented and tested.
- The extension smoke test remains green.

**Evidence.** Runtime/adapter integration tests with a cycle-0 breakpoint, session-status tests,
timeout tests, extension smoke, and updated contracts.

**Dependencies and risks.**

- WL-1.1 is delivered; WL-1.2 uses the start-gated launch behavior and adds no wire revision.
- Debug is local-only and one session per host; every swap, rollback, cold install, shutdown, or
  target exit ends the session and clears forces and breakpoints.
- `[debug].session-timeout` is opt-in and disabled by default because an automatic resume must
  not restart machinery unexpectedly.
- The start-gate handshake must not break existing `stc-debug/1` clients.

**Open planning questions.**

- Is start-paused a new protocol message, a launch flag, or an adapter-side wait for a ready
  event?
- Does it apply to attach as well as launch, and to release monitoring?
- Should the timeout warning be a Debug Console line, a notification, or both?
- Does F-15 need a protocol change, or only adapter and extension reporting?

**Implementation decisions (2026-11-04; manual check approved 2026-11-05).**

- Start-paused binding is a driver/host start-gate handshake, not a protocol message. The host
  publishes its debug endpoint, parks before cycle 0, and services the debug command queue; the
  driver releases the gate after `session.start`, `manifest.get`, and every pre-`configurationDone`
  breakpoint (plus `stc debug` `--break`/`--watch` setup). `stc-debug/1` and `stc-debug/1.1` are
  unchanged; no protocol revision was added.
- Launch means `stc dap` launch (including `test` and `noBuild`) and `stc debug` launch. Attach
  (`stc dap` attach, `stc debug --attach`, and `stc run --debug-server` hosts) cannot gate an
  already-running host and binds at the next checkpoint.
- The gate budget is 30 seconds (internal `--start-gate-timeout`). A host that is never released
  prints an error, shuts down, and exits 2 without running a cycle.
- F-15 is adapter-side. Every teardown emits one Debug Console summary that distinguishes a client
  stop, a host exit with its code, a trap (exit code 4), a swap/timeout with its code, and a
  connection loss; a launch-owned exit code is also sent as the DAP `exited` event. Attach reports
  that the host was left running.
- The optional `[debug].session-timeout` warning is implemented as a launch-session Debug Console
  line. The adapter reads the manifest default and honors a `--debug-session-timeout` host
  argument; it does not claim a countdown, and an attach session stays silent because it cannot
  know the running host's bound.
- Evidence: runtime start-gate and option tests; DAP cycle-0, terminate/exit, timeout-line,
  no-build, and test-launch tests; `stc debug` batch cycle-0 read; updated Debug and Monitoring,
  IDE Integration, CLI and Manifest, User Guide, extension README, and Known Limitations.
- Manual check: launch the sample workspace with a first-statement breakpoint and confirm the
  first stop reports cycle-0 values; stop the session and confirm the Debug Console names the
  client stop and host exit code; attach and confirm next-checkpoint binding; enable
  `[debug].session-timeout` and confirm the startup line.

## 5. Sequencing

The targets are independent enough to parallelize, but the following order retires risk and
builds shared foundations first.

1. **Quick wins and platform coverage.** WL-16, WL-17, WL-18, and the WL-14 CI-matrix work can
   start immediately. WL-16 establishes the debug-session behavior WL-1.2 will reuse; WL-17 and
   WL-18 improve the local IDE without new network or hardware surface.
2. **Runtime and I/O.** WL-7 and WL-15 can proceed in parallel on the delivered I/O contracts.
   WL-14's scheduling measurements follow its CI-matrix work and use the existing WL-4 harness.
3. **Remote access.** WL-1.2 is delivered (PR #25) using an SSH tunnel to the existing loopback
   debug socket. WL-15 follows on its broker TLS and credential track and shares the
   threat-model and secret-handling stance, not the SSH transport.
4. **Release.** Consolidate durable contracts and evidence, run the full CI matrix and package
   smoke, complete the release checklist, and retire this working document.

Cross-target work is tracked in §6; no target is a prerequisite of another except the shared
security stance and the delivered WL-16 debug-session behavior.

## 6. Cross-target decisions

- **One remote-access security stance for WL-1.2 and WL-15.** Threat model, authorization,
  secret storage, loopback defaults, explicit network opt-in, audit, and rate limits are agreed
  together. WL-1.2 delivered the SSH transport and identity model; WL-15 uses broker TLS and
  credentials. A WebUI or tracing surface is not in v3, so no second network service is
  introduced.
- **WL-1.2 added no debug-protocol revision.** The SSH tunnel carries the existing loopback
  `stc-debug/1.1` socket; the token, scopes, limits, and audit are unchanged. WL-16 delivered
  start-paused binding as a driver/host handshake, and WL-1.2 consumed that session behavior.
  Remote transport remains a driver-side concern, not a wire change.
- **Manifest contract changes go through WL-17.** `STC-E-PROJECT-004`, optional project items,
  and error timing are CLI/LSP/task-provider contracts; update the conformance profile and all
  consumers together.
- **Untrusted-input handling is shared.** WL-7 ESI parsing and WL-15 payload decoding use the
  project's bounded, fuzzed parser patterns; no target may silently ignore malformed input.
- **Evidence and registry updates are part of each target.** Decisions, architecture contracts,
  verification reports, and known limitations are updated as the target lands, not left for the
  end.

===============================================

Date: 2026-11-02

      processors), 16 GiB RAM, Windows 11 Pro 10.0.26300, x86_64
Toolchain: rustc 1.99.1 (58cf8f9c3 2026-10-13), cargo 1.99.1
Branch: WL-5.1
Harness: crates/stc-runtime/tests/modbus_overhead.rs
Build: release, #[ignore] test run explicitly

Command:

  cargo test -p stc-runtime --release --test modbus_overhead -- --ignored --nocapture

Configuration:
  one modbus-tcp device, bind 127.0.0.1:0, unit 1, max-connections 16,
  idle-timeout 30 s, device word-order low-first
  56 bound channels across coil, discrete-input, holding-register, and
  input-register tables; widths 1, 16, 32, and 64 bits
  process image: 48 bytes inputs, 64 bytes outputs
  iterations per client count: 200000 latch/publish pairs
  client mix per connection: FC1 coils @1024 qty 8, FC3 holding @1000 qty 8,
  FC4 input registers @0 qty 8, FC16 holding @0 qty 4 (round robin)

Method:
  The test constructs ModbusTcpBackend directly through the public
  DeviceBackend trait, runs its cold_start, and then measures the two
  cycle-boundary calls (latch_inputs and publish_outputs) in a tight loop.
  Client threads connect over loopback and issue the request mix while the
  main thread records per-call nanosecond samples. The harness also reads
  process CPU time with GetProcessTimes on Windows
  (clock_gettime(CLOCK_PROCESS_CPUTIME_ID) on Linux). No coordinator or
  scan engine is involved, so "cycle_mean" is the latch+publish seam cost
  only, not a scan period. Results are host-specific and are not a
  real-time or worst-case claim.

Columns:
  clients           connected client threads
  latch_p50_us      DeviceBackend::latch_inputs p50, microseconds
  latch_p99_us      latch p99
  latch_max_us      latch max
  publish_p50_us    DeviceBackend::publish_outputs p50
  publish_p99_us    publish p99
  publish_max_us    publish max
  cycle_mean_us     mean of latch+publish per iteration
  rtt_p50_us        client request round-trip p50 (0 for zero clients)
  rtt_p99_us        request round-trip p99
  rtt_max_us        request round-trip max
  requests_per_s    completed requests per wall second across clients
  process_cpu_s     process CPU time consumed during the whole row
  cpu_percent       process CPU time / wall time for the row

Interpretation
--------------
The seam cost stays in the low microseconds at p50 for every client count.
The p99 and max columns show scheduler and lock-contention outliers under
loopback load, especially at eight clients; they are not a cycle-time
guarantee. Request throughput is bounded by the synthetic per-connection
round-robin loop and the loopback stack, not by the cycle thread. CPU
percent is process-wide and includes every client and server thread.

No Linux host was available for this harness on 2026-11-02: the Windows
workstation was the only accessible machine, the WSL distribution was not
running, and ecat-host was not reachable by SSH or DNS from it. The
functional cross-host evidence is the CI matrix, not this timing file.

## 3. Release-level constraints

- **v1.0.0 is the compatibility baseline.** v2.0.0 is additive around the released compiler,
  runtime, artifact formats, and language profile.
- **No new core language or compiler features.** Compiler changes are limited to bug fixes and
  the instrumentation or public views required by a locked target.
- **WL-2 is a release gate.** The CI coverage job must be active and passing at 85% before
  v2.0.0 is released.
- **No deferred item may be pulled in** without an explicit re-plan of the target set.
- **WL-5.1 is network-facing.** Its authentication and trust boundaries must be documented; it is
  not a safety function.
- **WL-5.2 is Linux-only and IgH-dependent.** IgH licensing and packaging must be reviewed before
  implementation. Kernel-module compatibility is verified on the dedicated EtherCAT host
  (IgH 1.6.13 on `6.12.115-ecat-rt`), which is separate from the WL-4 host.
- **WL-4 evidence is host-specific.** Results apply to the x86-64 PREEMPT_RT host and configuration
  measured; no hard real-time or safety claim is made.
- **`stc` remains not a safety PLC.** Motion, debug, and I/O can hold outputs or move machinery;
  safety must come from a separate system and machine design.

### WL-1.1 — Local VS Code integration and debugging

**Locked scope.**

- Local-only VS Code extension: tasks and problem matchers for `stc check`, `build`, `run`,
  `test`, and `fmt`; diagnostics in the Problems panel; launch configurations.
- TextMate grammar for syntax highlighting.
- Language server (`stc-lsp`) for diagnostics, document symbols, go-to-definition, references,
  hover, completion, and `stc fmt` formatting.
- Debug adapter (`stc-dap`) translating DAP to the local `stc-debug/1` protocol: launch/attach,
  breakpoints, stepping, variables/watch, and call stack.
- Packaging as a VSIX or marketplace extension, with a sample ST workspace.

**Planned work.**

1. Decide the IDE-facing API boundary over the CST/HIR/sema crates (D-041) and whether the
   language server is a new crate or part of `stc-driver`.
2. Build the extension shell, tasks, problem matchers, and TextMate grammar.
3. Implement the language server and map diagnostics and navigation queries.
4. Implement the DAP adapter and document supported and unsupported capabilities.
5. Add smoke tests for diagnostics, navigation, formatting, and a local debug session.

**Exit criteria.**

- The extension installs and activates in VS Code.
- Syntax highlighting, diagnostics, go-to-definition, references, hover, completion, and
  formatting work on the sample workspace.
- A local debug session supports breakpoints, stepping, variables/watch, and call stack.
- The DAP capability mapping and packaging instructions are documented.
- Smoke tests run in CI or a documented local check.

**Dependencies and risks.**

- Depends on the existing local debug protocol and the public CST/IDE API decision.
- The extension must not become a second source of truth for diagnostics or types.
- Extension packaging, minimum VS Code version, and the local LSP transport remain planning
  inputs.

### WL-10 — Coverage emission for the ST test suite

Status: Done 2026-10-31; merged (PR #9). All exit criteria are met.

Report: [Testing and Verification](specification/Architecture/Testing-and-Verification.md) §2.6
records the coverage model, sites, instrumentation, collection protocol, aggregation, exclusions,
report formats, determinism, limitations, and evidence. The CLI surface and the `stc-coverage/1`
report shape are in [CLI and Manifest](specification/Architecture/CLI-and-Manifest.md) §1.1–§1.3,
§1.6, §2.4, and §4. Evidence: [examples/coverage/](examples/coverage/README.md) is the executable
example, and the committed golden reports under `crates/stc-driver/tests/coverage/expected/` are
checked by `crates/stc-driver/tests/coverage_evidence.rs`. D-211 records the two warning codes
`STC-W-COVERAGE-001/002`.

**Outcome.** The locked WL-10 decisions were implemented: codegen instruments executable
statement spans in test builds only through an exported module-owned counter array; the test host
writes a per-test `stc-coverage-raw/1` sidecar; the driver maps counters to canonical source spans,
aggregates across the suite, and writes deterministic `coverage.json` (`stc-coverage/1`),
`lcov.info` (LCOV), and a human summary under `target/stc/coverage`; `[test] coverage` and
`--coverage`/`--no-coverage`/`--coverage-out` control it; and `stc clean` removes the default
report directory. Instrumented tests keep the same statuses, failures, traps, cycles, and exit
codes as uninstrumented tests, and the reports contain no timings, build IDs, absolute paths, or
host data. No host ABI, GOT/manifest, metadata, production module, or test-result shape changed.
The enduring coverage model and formats are in the specifications above.

**Locked scope.**

- `stc test` emits coverage for the ST code under test, mapped to source spans.
- Test builds only; production builds and release artifacts are unchanged.
- Statement coverage first; branch coverage is a follow-on if the first format supports it.
- Per-test counters collected by the process-isolated runner and aggregated across the suite.
- Native JSON first; LCOV and a human/HTML summary may follow.

**Planned work.**

1. Choose the instrumentation point in HIR or codegen and the counter representation.
2. Map counters to ST source file, line, and column through the span table.
3. Extend the test host/runner to collect and aggregate per-test counters.
4. Add the `stc test --coverage` surface and report formats.
5. Define exclusions for test POUs, synthetic wrappers, and generated helpers; decide dependency
   and standard-library handling.
6. Add golden reports, aggregation, determinism, cross-host, and example-project tests.

**Exit criteria.**

- Coverage is emitted for a test build and maps to ST source spans.
- Per-test and suite-level results are available.
- Instrumented tests produce the same pass/fail, trap, and timing semantics as uninstrumented
  tests.
- Production builds and release artifacts contain no coverage instrumentation.
- Report formats and exclusion rules are documented and tested.

**Dependencies and risks.**

- Depends on the test runner, HIR span table, and codegen instrumentation points.
- Instrumentation overhead, standard-library and dependency inclusion, and report attribution are
  the main risks.
- Coverage is not a correctness claim and is separate from WL-2's compiler coverage.

## 5. Sequencing

- WL-1.1, WL-3, WL-5.1, WL-5.2, and WL-10 can start independently once their planning decisions
  are resolved.
- WL-2 is continuous and runs alongside every target; the CI gate is a release blocker.
- WL-4 is complete; its measurement harness and runbook are the pattern for WL-5.2, but WL-5.2
  runs on the separate `ecat-host` (IgH 1.6.13, kernel `6.12.115-ecat-rt`).
- WL-5.2 depends on the delivered EtherCAT hardware, the IgH licensing/packaging review, and the
  device-tree-to-IgH mapping. WL-7 (ESI) is not required for the static-configuration path.
- WL-5.1 and WL-5.2 share the runtime I/O binding layer and are expected to run in parallel.
  WL-5.2 delivers only the EtherCAT backend, but the layer is multi-backend from the start, so
  the Modbus TCP backend can attach without changing the EtherCAT backend.
- No locked target depends on a deferred item.

## 1. Locked targets

The v2.0.0 target set is locked. It was re-planned on 2026-10-31: WL-9 was removed and WL-5.2
was added. These seven items define the release scope.

| ID | Target | Locked scope | Primary evidence |
| --- | --- | --- | --- |
| WL-1.1 | Local VS Code integration and debugging | Local-only extension: TextMate grammar, language server, DAP adapter over the local `stc-debug/1` protocol, tasks, diagnostics, packaging | Installable extension, LSP/DAP smoke tests, sample workspace |
| WL-2 | Test coverage to 85% | 85% line coverage as reported by the existing CI coverage badge; the existing coverage job becomes a pass/fail gate | CI coverage job fails below 85% and passes at or above it |
| WL-3 | Lean verification P0.4 | Target syntax and `WellFormed` only: `IRFrag`, `WellFormed`, slot/cell model, structural lemmas | Lean build with no `sorry`, registry entries, P0.4 review |
| WL-4 | RT verification on x86-64 PREEMPT_RT | Run artifacts only on the available x86-64 PREEMPT_RT host; measure cycle timing, jitter, and latency | Reproducible report, harness, host baseline, runbook |
| WL-5.1 | Modbus TCP server I/O | Server role on all supported hosts; non-real-time; no client/master capability | Simulator and cross-host tests, error paths, cycle-overhead measurements |
| WL-5.2 | EtherCAT I/O on Linux using IgH | Linux-only IgH backend: cyclic process data and servo-drive integration, device-tree mapping, faults/recovery | IgH runbook, hardware-in-the-loop tests, cycle timing evidence, specification updates |
| WL-10 | Coverage emission for the ST test suite | `stc test` coverage for ST code under test, mapped to source spans; test builds only | Golden reports, aggregation tests, cross-host tests |

Locked scope is fixed. Adding or removing a target requires an explicit re-plan, not an edit to
this list.

## 2. Not in v2.0.0

The following items are deferred and are not part of v2.0.0:

- WL-1.2 — Remote IDE debugging.
- WL-6 — Motion controller.
- WL-7 — ESI-based EtherCAT device configuration.
- WL-8 — Tracing UI.
- WL-9 — WebUI for basic runtime control.
- WL-11 — Modbus TCP client capability.

They remain in [FutureWishlist.md](FutureWishlist.md) for a future version.

## 3. Release-level constraints

- **v1.0.0 is the compatibility baseline.** v2.0.0 is additive around the released compiler,
  runtime, artifact formats, and language profile.
- **No new core language or compiler features.** Compiler changes are limited to bug fixes and
  the instrumentation or public views required by a locked target.
- **WL-2 is a release gate.** The CI coverage job must be active and passing at 85% before
  v2.0.0 is released.
- **No deferred item may be pulled in** without an explicit re-plan of the target set.
- **WL-5.1 is network-facing.** Its authentication and trust boundaries must be documented; it is
  not a safety function.
- **WL-5.2 is Linux-only and IgH-dependent.** IgH licensing and packaging must be reviewed before
  implementation, and kernel-module compatibility with the RT host must be verified.
- **WL-4 evidence is host-specific.** Results apply to the x86-64 PREEMPT_RT host and configuration
  measured; no hard real-time or safety claim is made.
- **`stc` remains not a safety PLC.** Motion, debug, and I/O can hold outputs or move machinery;
  safety must come from a separate system and machine design.

## 4. Target plans

Each section records the locked scope and the first planning outline. Work breakdown, effort,
owners, and final exit criteria are refined here before implementation starts.

### WL-1.1 — Local VS Code integration and debugging

**Locked scope.**

- Local-only VS Code extension: tasks and problem matchers for `stc check`, `build`, `run`,
  `test`, and `fmt`; diagnostics in the Problems panel; launch configurations.
- TextMate grammar for syntax highlighting.
- Language server (`stc-lsp`) for diagnostics, document symbols, go-to-definition, references,
  hover, completion, and `stc fmt` formatting.
- Debug adapter (`stc-dap`) translating DAP to the local `stc-debug/1` protocol: launch/attach,
  breakpoints, stepping, variables/watch, and call stack.
- Packaging as a VSIX or marketplace extension, with a sample ST workspace.

**Planned work.**

1. Decide the IDE-facing API boundary over the CST/HIR/sema crates (D-041) and whether the
   language server is a new crate or part of `stc-driver`.
2. Build the extension shell, tasks, problem matchers, and TextMate grammar.
3. Implement the language server and map diagnostics and navigation queries.
4. Implement the DAP adapter and document supported and unsupported capabilities.
5. Add smoke tests for diagnostics, navigation, formatting, and a local debug session.

**Exit criteria.**

- The extension installs and activates in VS Code.
- Syntax highlighting, diagnostics, go-to-definition, references, hover, completion, and
  formatting work on the sample workspace.
- A local debug session supports breakpoints, stepping, variables/watch, and call stack.
- The DAP capability mapping and packaging instructions are documented.
- Smoke tests run in CI or a documented local check.

**Dependencies and risks.**

- Depends on the existing local debug protocol and the public CST/IDE API decision.
- The extension must not become a second source of truth for diagnostics or types.
- Extension packaging, minimum VS Code version, and the local LSP transport remain planning
  inputs.

### WL-2 — Test coverage to 85%

**Locked scope.**

- One headline target: 85% line coverage as reported by the existing CI coverage badge.
- The existing coverage job becomes a pass/fail gate at 85%; the measurement mechanism, badge,
  and reporting output do not change.
- Work is ranked by uncovered line count, with a small criticality boost for core pipeline and
  security-adjacent files. Tooling such as `xtask` does not outrank product code.
- No per-crate, per-host, region, or other secondary targets.

**Planned work.**

1. Keep the baseline and ranked gap list current from each CI coverage report.
2. Close the highest-value gaps first, starting with the largest product-code gaps.
3. Add focused unit, property, differential, and negative tests; reuse fuzz and conformance
   corpora.
4. Add the 85% failure condition to the existing coverage job.
5. Make the coverage job a required branch-protection check for pull requests and `main`.

**Exit criteria.**

- The CI coverage job fails when the reported badge figure is below 85%.
- The job passes at or above 85% on the release commit.
- The badge and reporting output are unchanged in meaning.
- Test additions exercise behavior and error paths, not just lines.
- The passing coverage figure is recorded in the release evidence.

**Dependencies and risks.**

- Depends only on the existing coverage job and tests.
- The runtime/debug block is the largest cluster; unit tests come first for isolatable logic, with
  integration harness work only where a session or transport boundary is required.
- The main risk is inflating low-value tests; the ranking rule and review guard against it.

### WL-3 — Lean verification P0.4

**Locked scope.**

- P0.4 only: target syntax and well-formedness for the emitted-IR fragment.
- Define `IRFrag`: modules, type definitions, globals, constants, functions, basic blocks,
  instructions, terminators, and the slot/function tables.
- Define `WellFormed`: type correctness, SSA/dominance, block terminators, `phi` arity, GOT cell
  kinds, canonical slot table, entry-point signatures, and no direct persistent-root or
  user-callable references.
- Define the slot table and cell-kind model, and prove the structural lemmas in
  [Plan-Phase0 §P0.4](specification/Verification/Plan-Phase0.md).
- P0.5 target semantics, P0.6 conformance, P0.7 review/versioning, and later phases are out of
  scope.

**Planned work.**

1. Fix the `IRFrag` type definitions and the slot/cell model in Lean.
2. Align the `WellFormed` predicate with the current `stc-codegen` verifier and the ABI 2
   contract, documenting intentional differences.
3. Prove the structural lemmas with no `sorry` or `admit`.
4. Register every new theorem and definition in `lean/verification-status.toml`.
5. Update the semantics document where P0.4 changes vocabulary or the checked fragment.

**Exit criteria.**

- `IRFrag` and `WellFormed` are defined and compile.
- The P0.4 structural lemmas are proved with no `sorry` or `admit`.
- The Lean build and registry checks pass in CI.
- The P0.4 review is approved and recorded.
- No compiler or language change is required beyond bug fixes or instrumentation.

**Dependencies and risks.**

- Depends on the P0.0/P0.1 vocabulary, not on the paused P0.3 work.
- The main risks are specification ambiguity and divergence from the Rust verifier; both are
  resolved before the proofs scale.

### WL-4 — RT verification on x86-64 PREEMPT_RT

Status: Done 2026-10-30. All exit criteria are met.

Report: [RT-Host.md](specification/Verification/RT-Host.md) records the untuned campaign evidence
and the deferred tuned-profile evaluation. Runbook:
[RT-Runbook.md](specification/Verification/RT-Runbook.md). Evidence:
[RT-Run-Manifest.md](specification/Verification/RT-Run-Manifest.md).

**Outcome.** The locked decisions were implemented: CI-built Linux package and `rt-bench` bundle;
a root-owned measurement wrapper with a narrow NOPASSWD rule; an opt-in RT mode (`--rt`,
`--rt-priority`, `--rt-cpu`, `--rt-metrics`) and the `stc-rt-metrics/1` schema; a Python harness
for the untuned R0/R1/R2 campaign, online change, rollback, and control/status cost; and the
report, performance, and limitations updates. The tuned boot profile remains deferred future
work: the trigger is met by the untuned R1 heavy mixed-load and osnoise results, but it was not
executed in v2.0.0. No hard real-time or safety claim is made.

**Locked scope.**

- Run artifacts on the available x86-64 PREEMPT_RT Linux host; build only on development or CI
  hosts.
- Measure cycle wake-up jitter, cycle execution time distribution, missed deadlines, page faults
  and allocations in steady state, and control/status-thread cost.
- Cover `stc run`, online change prepare/activation, and rollback under load.
- Deliver a reproducible report, harness, and host runbook.
- No hard real-time guarantee and no safety claim.

**Planned work.**

1. Define the artifact transfer and verification procedure for the x86-64 host.
2. Record the host baseline: CPU, kernel and PREEMPT_RT configuration, isolation, affinity,
   governor, and `cyclictest`.
3. Build the benchmark project and machine-readable harness.
4. Run the measurement campaign, including swap and rollback under load.
5. Write the report with method, environment, raw data, and limits.

**Exit criteria.**

- The artifact pipeline is documented and reproducible.
- The harness produces comparable, machine-readable results.
- The report states the host configuration and the measured distributions.
- Online change and rollback are measured under load.
- The runbook explains how to repeat the campaign without using the host as a build environment.

**Dependencies and risks.**

- Depends on access to the x86-64 RT host and compatible build artifacts.
- Host configuration, transfer, and cross-host compatibility are the main risks.
- Results remain host- and configuration-specific.

### WL-5.1 — Modbus TCP server I/O

**Locked scope.**

- Server role only: expose the `stc` process image to Modbus TCP clients.
- All supported hosts: Windows x86-64 MSVC, Linux x86-64 GNU, Linux AArch64 GNU.
- Non-real-time, best-effort behavior; not an interpolated motion channel.
- No client/master capability (WL-11 is deferred).
- Use the existing device/binding and metadata model where possible; keep protocol details out of
  the language and compiler.

**Planned work.**

1. Define the server mapping from process-image ranges to coils, discrete inputs, holding
   registers, and input registers.
2. Implement the backend and request scheduling at the cycle boundary.
3. Define connection limits, timeouts, idle/failure behavior, byte/word order, and diagnostics.
4. Add simulator, error-path, cross-host, and cycle-overhead tests.
5. Update the I/O specification and [KNOWN-LIMITATIONS.md](KNOWN-LIMITATIONS.md).

**Exit criteria.**

- The server backend works on all three native hosts.
- Simulator tests cover reads, writes, malformed requests, disconnects, and reconnects.
- Request handling does not silently corrupt process-image values.
- The backend is documented as non-real-time.
- The I/O specification and known-limitations list are updated.

**Dependencies and risks.**

- Depends on the runtime backend contract and process-image model.
- The main risks are request scheduling relative to input latch/output publish, connection
  handling, and the absence of standard transport security.
- The server mapping model (existing bindings versus a separate mapping) is a planning decision.

### WL-5.2 — EtherCAT I/O on Linux using IgH

**Locked scope.**

- Linux-only EtherCAT I/O backend on the IgH EtherCAT master, including cyclic process data and
  servo-drive integration; no EtherCAT master, slave stack, or raw protocol engine is implemented
  in-project.
- Map the `stc.toml` device tree and channel descriptors to IgH configuration and process data;
  keep protocol details out of the language and compiler.
- Cyclic process data latched and published at the cycle boundary, with startup, fault, recovery,
  and shutdown ordering. Use distributed clocks where IgH provides them.
- Static EtherCAT configuration first; ESI-based device configuration (WL-7) remains deferred and
  is not required for this scope.
- Simulator or loopback tests where hardware is unavailable, plus hardware-in-the-loop tests on
  the PREEMPT_RT host (WL-4) and I/O-cycle timing and jitter measurements.
- No motion controller (WL-6) and no safety function.

**Planned work.**

1. Review IgH licensing and packaging, and select the IgH version and link model (shared library,
   static library, or daemon interface).
2. Define the static device-tree and channel-descriptor mapping to IgH configuration and PDO
   layout; decide where ESI validation will attach when WL-7 lands.
3. Implement the backend: initialization, cyclic latch/publish, health/status, fault and recovery,
   and startup/shutdown ordering with the runtime host.
4. Define behavior for online change and rollback when topology or bindings cannot be preserved.
5. Add loopback or simulator tests, error-path tests, hardware-in-the-loop tests, and
   cycle-overhead measurements.
6. Write the IgH setup runbook and hardware/software baseline; update the I/O specification and
   [KNOWN-LIMITATIONS.md](KNOWN-LIMITATIONS.md).

**Exit criteria.**

- The backend runs on the Linux host with IgH and the available EtherCAT hardware.
- Cyclic process data is latched and published deterministically at the cycle boundary.
- Startup, fault, recovery, and shutdown paths are tested; fieldbus failure cannot silently
  corrupt process-image values.
- The device tree and channel descriptors map to IgH configuration without protocol details
  leaking into the language or compiler.
- Hardware-in-the-loop tests and I/O-cycle timing and jitter measurements are recorded.
- The IgH licensing and packaging review is complete, and the runbook and specification updates
  are reviewed.
- The backend is documented as Linux-only and not a safety function.

**Dependencies and risks.**

- Depends on WL-4 (done) for the PREEMPT_RT host, on IgH, and on the delivered EtherCAT hardware.
- IgH kernel-module compatibility with the RT kernel, hardware and slave configuration, licensing
  and packaging, and online-change behavior across topology changes are the main risks.
- Static configuration is the v2.0.0 path; WL-7 (ESI) is deferred, so device configuration is
  hand-maintained.
- Results remain host- and hardware-specific; no hard real-time or safety claim is made.

### WL-10 — Coverage emission for the ST test suite

Status: Done 2026-10-31. All exit criteria are met.

Report: [Testing and Verification](specification/Architecture/Testing-and-Verification.md) §2.6
records the coverage model, sites, instrumentation, collection protocol, aggregation, exclusions,
report formats, determinism, limitations, and evidence. The CLI surface and the `stc-coverage/1`
report shape are in [CLI and Manifest](specification/Architecture/CLI-and-Manifest.md) §1.1–§1.3,
§1.6, §2.4, and §4. Evidence: [examples/coverage/](examples/coverage/README.md) is the executable
example, and the committed golden reports under `crates/stc-driver/tests/coverage/expected/` are
checked by `crates/stc-driver/tests/coverage_evidence.rs`. D-211 records the two warning codes
`STC-W-COVERAGE-001/002`.

**Outcome.** The locked decisions C-1–C-14 were implemented: codegen instruments executable
statement spans in test builds only through an exported module-owned counter array; the test host
writes a per-test `stc-coverage-raw/1` sidecar; the driver maps counters to canonical source spans,
aggregates across the suite, and writes deterministic `coverage.json` (`stc-coverage/1`),
`coverage.info` (LCOV), and a human summary under `target/stc/coverage`; `[test] coverage` and
`--coverage`/`--no-coverage`/`--coverage-out` control it; and `stc clean` removes the default
report directory. Instrumented tests keep the same statuses, failures, traps, cycles, and exit
codes as uninstrumented tests, and the reports contain no timings, build IDs, absolute paths, or
host data. No host ABI, GOT/manifest, metadata, production module, or test-result shape changed.
The working plan [WL-10-Plan.md](WL-10-Plan.md) remains as a record; the enduring coverage model
and formats are in the specifications above.

**Locked scope.**

- `stc test` emits coverage for the ST code under test, mapped to source spans.
- Test builds only; production builds and release artifacts are unchanged.
- Statement coverage first; branch coverage is a follow-on if the first format supports it.
- Per-test counters collected by the process-isolated runner and aggregated across the suite.
- Native JSON first; LCOV and a human/HTML summary may follow.

**Planned work.**

1. Choose the instrumentation point in HIR or codegen and the counter representation.
2. Map counters to ST source file, line, and column through the span table.
3. Extend the test host/runner to collect and aggregate per-test counters.
4. Add the `stc test --coverage` surface and report formats.
5. Define exclusions for test POUs, synthetic wrappers, and generated helpers; decide dependency
   and standard-library handling.
6. Add golden reports, aggregation, determinism, cross-host, and example-project tests.

**Exit criteria.**

- Coverage is emitted for a test build and maps to ST source spans.
- Per-test and suite-level results are available.
- Instrumented tests produce the same pass/fail, trap, and timing semantics as uninstrumented
  tests.
- Production builds and release artifacts contain no coverage instrumentation.
- Report formats and exclusion rules are documented and tested.

**Dependencies and risks.**

- Depends on the test runner, HIR span table, and codegen instrumentation points.
- Instrumentation overhead, standard-library and dependency inclusion, and report attribution are
  the main risks.
- Coverage is not a correctness claim and is separate from WL-2's compiler coverage.

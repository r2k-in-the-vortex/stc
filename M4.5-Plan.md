M4.5 is inserted between M4 and M5. It converts the completed scalar codegen path to the
persistent host + loadable module model and establishes the GOT, manifest, and swap protocol that
every later M5 feature must use. **M5 must not start until M4.5's exit criteria pass.**

## 1. Objective

Deliver a working online-change foundation for the M4 scalar surface:

- a persistent host runtime that owns the cycle, GOT, memory, modules, state, I/O, and services;
- loadable whole-program modules with a versioned descriptor and host ABI 2;
- host-owned GOT cells, per-field scalar roots, and stable storage;
- a persistent GOT manifest emitted by the compiler and consumed as the next build's baseline;
- background load/prepare, O(1) cycle-boundary activation, one-successful-cycle rollback, and
  off-thread unload;
- exact-baseline compatibility, tracked rename/move, preserve/allocate/drop, and cold download;
- tests and documentation for all of the above on Windows MSVC x64 and Linux GNU x64.

## 3. Architecture summary

```text
compiler: HIR -> IR + identity/catalog -> module descriptor + manifest pair
host:     load/validate -> attach -> prepare (temp GOT) -> cycle boundary switch
          -> one successful cycle -> commit -> grace -> unload
```

- The host owns the GOT cell table, root allocator, manifest store, process image, state, and
  loader/service threads.
- The module owns code and version-local read-only data; it never owns persistent storage.
- A cell is a stable host-owned pointer-sized slot. Generated code reads cells; only the host
  writes them.
- Persistent scalar globals/program fields become per-field roots with `GotId`s. A root's storage
  is stable; removed roots are quarantined.
- The module slot table maps local slots to host cells. Slot numbers are not stable across builds;
  `GotId` is.
- The manifest is the identity/history artifact; the module descriptor is the minimal
  code-address/entry-point binding. Both pair by digest.
- Activation uses normal/temp GOT generations and an O(1) pointer swap at the cycle boundary.

## 4. Exit criteria

1. `stc build --emit=module` produces a loadable module, metadata, and a complete GOT manifest for
   the M4 scalar surface; a cold build without a baseline still emits a complete manifest.
2. A second build consumes the first manifest, reuses every unchanged `GotId`, and emits a new
   manifest plus an online-change plan.
3. The host loads a module, runs cycles, loads a second module, preserves matching scalar roots,
   swaps at a cycle boundary, stores the new active manifest, and unloads the old module.
4. A code-only change preserves all matching state; a new global initializes; a removed global is
   quarantined with a warning.
5. A tracked rename preserves the `GotId` and value; an untracked rename is diagnosed and
   requires an explicit policy.
6. A layout/type change is rejected by default; the old version continues.
7. A missing, stale, tampered, unpaired, or non-current manifest selects cold download; no
   online-change recovery, merge, or partial attempt occurs.
8. The active manifest can be exported/downloaded and used as the baseline for another build,
   producing identical `GotId`s for matching declarations.
9. A failed prepare or load leaves the old version active and intact.
10. Internal host allocations are transient: reclaimed on failed prepare, retire, or unload; no
    persistent root or manifest entry may reference them.
11. A structural test proves no persistent root or user function is directly referenced in
    generated IR.
12. Two builds of the same source and baseline produce identical IR, descriptors, manifest,
    online-change plan, metadata, and build IDs.
13. Existing M4 execution behavior is preserved through the host/module path, including traps,
    process image, exports, and scalar retain stubs.
14. `cargo test --workspace --locked`, clippy, fmt, docs checks, Markdown lint, and fuzz smoke
    pass.
15. README, project plan, architecture, runtime, state, I/O, CLI, testing, decisions, and M5
    handover reflect the new model.
16. `--emit=exe` produces a thin host launcher for an adjacent module pair; `--emit=lib` produces
    the embedding host library with the generated module kept separate; `exe` and `lib` may be
    emitted together.

## 6. Compiler work

### 6.1 Identity and manifest model

- Add a compiler-owned identity pass after semantic analysis that walks persistent declarations
  and produces catalog records for roots, functions/methods/FB bodies, types/descriptors,
  instances, tasks, and exports.
- `GotId = H(scope, current key, kind)` content-derived 128-bit value with collision checking.
  Data/type IDs exclude current type/layout; function IDs include the signature.
- Consume a baseline manifest (`--got-manifest` or the default active path). Match by `GotId`
  and/or current key; apply explicit rename/move maps. Never use heuristic rename detection.
- Classify each identity as preserve, allocate, drop, retire, reset, reject, or cold. Type/layout
  changes are reject/reset in v1; untracked removals require `--allow-untracked-removal` or
  `--cold`.
- Emit canonical JSON and compact binary from one deterministic model. Include header/lineage,
  identity/layout/function/type/instance/task/export records, slot mappings, plan, history, and
  digests. No runtime values.

### 6.2 Codegen

- Replace direct global/instance access with slot-table load + cell load + storage access.
- Replace direct user/standard function calls with indirect calls through function cells.
- Emit the per-module slot table, module descriptor, GOT metadata, and structural invariants.
- Convert I/O image base, retain buffer, task guards, and export bindings to the host/module model.
- Keep M4's deterministic IR and diagnostic behavior; M4-only constructs remain rejected.
- Emit debug/checkpoint hooks as no-ops or lightweight calls that M6.5 can activate; do not
  implement the full debugger here.

### 6.3 Driver and CLI

- Add `--emit=module`, `--got-manifest <path>`, `--cold`, `--rename old=new` (repeatable), and
  `--allow-untracked-removal`.
- Expose manifest export/download and diff data through the host API and test entry points; the
  user-facing `stc online download/diff` commands land in M6.
- Keep the M4 `--emit` kind names (`ir`, `obj`, `module`, `exe`, `lib`, `metadata`). `exe`
  becomes a thin host launcher and `lib` becomes the embedding host library; generated code
  remains in the separate loadable module. The M4 code-linked executable/library artifacts are
  retired. `exe` and `lib` may be emitted together.
- Emit module/metadata/manifest deterministically and report compatibility status.

## 7. Runtime work

### 7.1 Host and GOT

- Host state: GOT cells, slot-table installation, root registry, allocator, quarantine,
  generation records, manifest store, process image, state, task state, and services.
- Host-only cell writes under the control lock. Cells are stable; storage never moves.
- Root allocation is zeroed and stable. New roots initialize once; preserved roots are not
  reinitialized; removed roots quarantine until restart/explicit reset.
- Transient alloc/free is module-version-owned; reject unknown/double frees; refuse to register
  transient storage as a persistent root.

### 7.2 Module lifecycle

- Validate magic/version/ABI/profile/target/build ID/manifest digest/entry points/slot counts.
- Attach passes the host API and GOT context. Prepare builds the temp GOT and candidate roots.
- Activation switches at the cycle boundary; retain the old generation for one successful cycle.
- Commit stores the active manifest atomically; unload waits for grace and generation pins.
- Load/prepare failures are non-fatal; the active generation continues.
- Generation pinning/epoch refcounts protect service readers; no cycle-blocking locks.

### 7.3 Compatibility and state

- Preserve roots matching `GotId`, type key, layout hash, and size.
- Reject incompatible layout/type changes by default; explicit per-field reset only.
- Online attach skips state-file load; cold download applies defaults and compatible `RETAIN`.
- Reconfigure the process image, preserve `%M`/same-address variables, remap direct cells, warn
  on remaps.
- No field-layout or retained-state migration in v1.

### 7.4 Host services and threads

- Versioned host API table with trap/clock/state/I/O/alloc/free/GOT/ref-resolver/typed access.
- Loader/prepare thread and lower-priority service/monitor threads.
- Lock-free counters/double-buffered snapshots/bounded rings for status; no cycle blocking.
- Debug hooks are present but inactive; M6.5 builds the full debugger on this boundary.

## 8. Test plan

### 8.1 Structural and determinism

- No direct persistent-root/function references in generated IR.
- Every persistent place has a slot/cell path; every call has a function cell.
- Every root has one catalog entry; every entry has a unique `GotId`; descriptor/manifest pair.
- Byte-identical double builds for module, metadata, manifest, and plan.
- Baseline consumption produces identical `GotId`s for unchanged declarations.

### 8.2 Runtime unit tests

- Cell allocation/stability; slot-table remapping.
- Root matching/allocation/initialization/quarantine/reset.
- Malformed descriptor/manifest: magic, version, target, counts, offsets, duplicates, truncation,
  digest/parent mismatch, tampered plan.
- Swap state machine: load/validate/attach/prepare/activate/commit/rollback/unload.
- Function-cell updates and rollback snapshots.
- Process-image reconfiguration, clock continuity, watchdog policy.
- Transient allocation lifetime and rejection paths.
- Generation pinning under a concurrent reader.

### 8.3 Execution and hot-swap

Build at least two versions of a small program with a counter, timer-like state, exported
function, `%M` marker, and scalar retain leaf. Cover:

- cold install, code-only swap, new/removed global, tracked rename/move;
- untracked rename/removal diagnosis and explicit allow/cold;
- incompatible type/layout change rejection and reset path;
- missing/stale/tampered baseline cold download;
- prepare failure and rollback-window trap;
- manifest export/download and rebuild from it;
- the thin `exe` launcher and the embedding `lib` host load the same module, including a build
  that emits both;
- direct-variable remap and I/O reconfiguration;
- O(1) switch and bounded maintenance jitter (measurement recorded).

### 8.4 CI

- Both Windows x64 and Linux x64.
- Unit, snapshot, execution, hot-swap, manifest, determinism, fuzz-smoke, docs, clippy, fmt.
- Launcher and embedding-host artifact tests run on both hosts.
- Corrupt manifest/descriptor fuzz targets; no native module execution in fuzzers.

## 9. Risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Slot/identity mismatch | Preserved values bind to wrong storage | Content `GotId`s; exact type/layout checks; structural verifier; reject on mismatch |
| Manifest loss/corruption | Forced cold restart | Immutable versioned files + active copy; digests; tested cold path; download/export |
| Loader/service interference | Cycle jitter | Lower priority/affinity; bounded queues; O(1) switch; measure jitter |
| Rollback window too short/long | Failed change escapes or state rolls back unnecessarily | One complete successful cycle; explicit commit; record failure |
| Direct-pointer leakage | Unload crashes or stale access | Structural no-direct-reference test; quarantine; generation pinning |
| ABI/schema churn | M4/M5 artifacts incompatible | ABI 2 + versioned descriptor/manifest; reject before attach |
| Test-only coverage | Bugs reach M5 | Hot-swap suite in normal CI on both hosts; negative/corrupt cases |
